1. Why this exists

A founder running Suby (a payments infra company) needs to track 50+ ongoing relationships with: payment processors (Stripe, Adyen), crypto custodians (Coinbase, Ledger), VCs (Sequoia, a16z), AI & infra partners (Mistral, Vercel, HF), and fintech adjacencies (Qonto, Ramp). Traditional CRMs (Salesforce, HubSpot) are built for sales pipelines, not relationship hygiene. Personal CRMs (Folk, Attio) are closer but still demand a lot of manual input.

The bet here is voice-first capture + proactive AI: send a voice note to a Telegram bot ("coffee with Patrick, follow up in 2 weeks"), the system extracts the action, links it to the right contact, and surfaces it on the Today view. The AI also nudges you to reach out to people you're letting go cold.

3. Architecture & mock-first pattern

Every page is built so it renders correctly even when the backend is down. The pattern is: 

// In any view's useEffect:
contactsApi.getAll(params)
  .then((res) => {
    if (res.data?.length) setContacts(res.data);   // real data wins
    else setContacts(mockFilteredContacts(params));  // fallback
  })
  .catch(() => setContacts(mockFilteredContacts(params)));
Why this matters for the dev: when you wire the real backend, you don't have to touch the components — once res.data has rows, the mock fallback disappears. To test a page with zero data, just empty the corresponding table.

6. Data models

Defined in src/lib/types.ts and mirrored in prisma/schema.prisma.

Contact

interface Contact {
  id: string;
  name: string;
  type: "vc" | "lead" | "partner" | "friend" | "prospect" | "team" | "advisor" | "media" | "other";
  domain: "payment" | "blockchain" | "saas" | "ecommerce" | "ai" | "marketing" | "legal" | "finance" | "other";
  company: string | null;
  role: string | null;
  relationshipStrength: "cold" | "warm" | "hot";
  aiSummary: string | null;
  lastContactDate: string | null;
  firstContactDate: string | null;
  contactFrequency: number | null;
  platforms?: Platform[];        // X, LinkedIn, Telegram, email handles
  interactions?: Interaction[];  // DMs / mentions with snippet + platform + direction
  notes?: Note[];                // free-form notes (supports #hashtags)
  contactTags?: ContactTag[];
}

Company

interface Company {
  id: string;
  name: string;
  sector: string | null;     // raw — see Network for the display taxonomy
  size: "startup" | "scaleup" | "enterprise" | null;
  funding: string | null;    // e.g. "series-c", "public"
  website: string | null;
  linkedin: string | null;
  description: string | null;
  contactCount?: number;
}

Reminder

interface Reminder {
  id: string;
  contactId: string;
  content: string;
  dueDate: string;             // ISO
  status: "pending" | "done" | "dismissed";
  contact?: { id: string; name: string };
}

CalendarEvent (Pre-call & Today)

interface CalendarEvent {
  id: string;
  title: string;
  start: string; end: string;
  contactId: string;
  contactName: string;
  channel: "zoom" | "meet" | "phone" | "in_person" | "telegram" | "x_space";
  location?: string;           // URL for zoom/meet, address otherwise
  description?: string;
}

Deal (Pipeline)

type DealStage = "intro" | "first_call" | "tech_review" | "term_sheet" | "live" | "lost";

interface Deal {
  id: string;
  companyId: string; companyName: string;
  contactId: string; contactName: string;
  stage: DealStage;
  value: number;          // monthly volume EUR
  probability: number;    // 0-100
  enteredStageAt: string;
  nextStep: string | null;
  source: "outbound" | "inbound" | "referral" | "event";
}

Sequence (proactive follow-up)

interface Sequence {
  id: string;
  contactId: string; contactName: string; company: string | null;
  goal: string;
  paused: boolean;
  steps: {
    index: number;
    channel: "email" | "linkedin" | "telegram" | "x";
    delayDays: number;
    scheduledFor: string;       // ISO
    status: "sent" | "scheduled" | "waiting" | "skipped";
    draft: string;              // the message text the user copies
    rationale: string;          // why this step / channel
  }[];
}

VoiceCapture

interface VoiceCapture {
  id: string;
  receivedAt: string;
  durationSec: number;
  transcript: string;
  status: "processed" | "needs_confirmation" | "failed";
  processingMs: number;
  actions: {
    kind: "note" | "reminder" | "strength_bump" | "tag" | "no_action";
    contactId: string | null; contactName: string | null;
    description: string;
    dueDate?: string | null;
    newStrength?: "cold" | "warm" | "hot";
    tag?: string;
  }[];
}

ReachOutSuggestion (AI scoring)

// Computed from MOCK_CONTACTS via computeSuggestions() in lib/mock-suggestions.ts
interface ReachOutSuggestion {
  contactId: string; contact: Contact;
  urgency: "high" | "medium" | "low";
  score: number;
  reason: string;        // e.g. "Cold for 87d · investor update overdue"
  channel: PlatformType | null;
  channelHandle: string | null;
  draftMessage: string;  // Template-based copy (varies by sector / type / strength)
  signals: string[];     // ["Cold for 6mo", "VC priority", …]
}

9. Production checklist

Grouped by effort. Things that align the prototype with the target stack are listed first.

Stack alignment (the must-dos)

  • × Migrate styling to Tailwind + shadcn/ui. The prototype uses inline CSS classes (.cd, .btn, .bdg, .tabs, .kpi, .tabs). Approach:
    • Map the CSS tokens in globals.css (--bd, --sf, --t1, etc.) onto the Tailwind theme.
    • Run npx shadcn@latest init then add components piece-by-piece: Button, Card, Tabs, Badge, Dialog, Tooltip, Sheet, Avatar, Input, Textarea, DropdownMenu.
    • Replace the bespoke kanban / modal / split-view components with shadcn primitives. Layout and behavior already validated — only the chrome changes.
  • × Wire better-auth. Single-user prototype today; in prod even a one-tenant CRM needs session protection.
    • Install better-auth + @better-auth/cli. Provider: email/password or Google (preferred since Calendar/Gmail already in scope).
    • Generate the Prisma schema add-ons (npx @better-auth/cli generate) and re-migrate.
    • Add the auth middleware on every /api/* route except /api/auth/*.
    • Build a minimal sign-in page; the dashboard layout already mounts a sidebar that can host a profile menu.
  • × Add Redis + BullMQ for jobs and cache.
    • Queues to create:
      • voice-capture: incoming Telegram voice → Whisper → Claude tool-use → persist.
      • ai-classify: batch contact classification (replaces the synchronous "Classify All" button).
      • ai-summary: per-contact AI summaries on demand.
      • ai-prep: per-event pre-call briefing generation (warm cache 30 min before).
      • enrich-contact: LinkedIn/X/website enrichment after creation.
      • sequence-tick: every hour, advance sequences whose next step is due (no auto-send — just status transitions).
      • daily-brief: cron at 7:55am, builds the brief, hands it to the bot for the 8am Telegram push.
      • outcome-prompt: 30 min after a calendar event ends, push the "How did it go?" prompt.
    • Cache keys: contact:{id}:summary, contact:{id}:briefing, suggestions:{userId} (15 min TTL).
    • Locally: docker run -p 6379:6379 redis. In prod: managed Redis on Scaleway or Upstash.
  • × Plan Supabase → Scaleway migration. Today DATABASE_URL + DIRECT_URL point at Supabase (eu-west-3). The schema is provider-agnostic (standard Postgres), so the migration is:
    • pg_dump → pg_restore against a fresh Scaleway managed Postgres instance.
    • Swap the two env vars. No code changes.
    • Drop the Supabase-specific helpers (auth, realtime, storage) — none are used here, so nothing to port.

Quick wins (½ day each)

  • × Replace process.env.NEXT_PUBLIC_API_URL || "http://localhost:4002" in lib/api.ts with an env-driven production URL.
  • × Set up .env: DATABASE_URL, DIRECT_URL, ANTHROPIC_API_KEY, NEXT_PUBLIC_API_URL, REDIS_URL, BETTER_AUTH_SECRET, BETTER_AUTH_URL.
  • × Run npx prisma migrate dev against an empty DB to generate the initial migration. Schema already declared.
  • × Add a seed script if you want demo data in the DB (today the mocks live only in lib/mock-*.ts).
  • × Hide or remove the mock fallback for production builds (gate the setContacts(mock…) calls behind NODE_ENV !== "production") — or keep them as a graceful empty state.

Medium (1–3 days each)

  • ● AI endpoints: wire /api/ai/classify, /summary, /prep to Anthropic. Service files exist as stubs — they just need a real Claude call with the contact context (interactions + notes + company). Once wired, push them through BullMQ workers (ai-classify, ai-summary, ai-prep queues).
  • ● Google Calendar integration for Pre-call: pull events for the next 14 days via OAuth, match attendees against contacts by email. The Settings card and the agenda view are already built. Use better-auth's Google provider to share the OAuth token.
  • ● Beeper import: extends what's already there (server/import/beeper.ts + POST /api/imports/beeper). Needs Matrix client credentials + bridge mapping. Run as a BullMQ job with progress reporting.
  • ● Persist Deals (Pipeline): add Prisma model, routes, swap MOCK_DEALS for API calls in pipeline-view.tsx.
  • ● Persist Sequences: add Prisma model + routes + the sequence-tick BullMQ job (advances status, no send). The UI is explicit that there's no auto-send.

Larger (1+ week)

  • × Voice capture pipeline (Telegram bot). Lives in the suby-operation repo. Path: Telegram voice message → enqueue on voice-capture queue (Redis/BullMQ) → worker calls Whisper → Claude tool-use (tools: upsertContact, createNote, createReminder, bumpStrength, addTag) → writes to suby-contacts Postgres + emits an SSE event to refresh the Voice page.
  • × Unified inbox: real connectors. Telegram (bot or MTProto), X (DM polling), Gmail (push notifications via Pub/Sub), LinkedIn (no public API → Unipile or manual). Each connector is its own BullMQ worker writing to an InboxMessage table.
  • × Meeting outcome loop: outcome-prompt queue fires 30 min after the Google Calendar event ends → push notification via the Telegram bot. Response updates strength + creates next-step reminder.
  • × Daily morning brief: daily-brief cron at 7:55am builds content + hands to the bot for the 8am Telegram push.
  • × Suggestions caching: move computeSuggestions() from client-side to a backend job; cache result in Redis (15 min TTL). Avoids recomputing on every Overview render once the data set grows.

Nice-to-have

  • × Real-time updates via SSE/WebSockets for the Inbox + Reminders pages (BullMQ events → SSE bridge).
  • × Mobile-friendly polish (sidebar already collapses; some pages need narrower layouts).
  • × Dark mode (CSS tokens are isolated in :root; map them on Tailwind dark: variants during the shadcn migration).
  • × Export contacts to CSV.
  • × Bulk actions on the contacts list (tag N contacts, delete N).

10. Setup & run

Prerequisites

  • Node 20+
  • A Postgres database (Supabase today; Scaleway managed Postgres planned). Existing dev DB ref: ypyrjbhhhlbtcuschjmy, eu-west-3.
  • Redis (for BullMQ jobs + cache). Local: docker run -p 6379:6379 redis.
  • Anthropic API key (Claude). OpenAI key for Whisper if running the voice pipeline locally.

Install

git clone <repo> suby-contacts
cd suby-contacts
npm install
cp .env.example .env.local   # see env table below
npx prisma generate
npx prisma migrate dev       # creates schema in your DB

Run (three processes)

# Terminal 1 · frontend on :3005
npm run dev

# Terminal 2 · backend on :4002
npm run dev:api

# Terminal 3 · Redis on :6379 (skip if you have one running)
docker run -p 6379:6379 redis

# (Once BullMQ workers are wired) Terminal 4 · workers
npm run dev:workers

Without the backend, the UI still fully works thanks to the mock fallbacks. With the backend and an empty database, you'll see empty states unless you seed. Redis isn't needed until the BullMQ queues (voice, AI batches, sequences, daily brief) are wired.

11. Test plan

What to click through after wiring the backend, to confirm nothing regressed.

  1. Boot empty — start with an empty DB. Every page should render. The mock fallback kicks in. ✓
  2. Seed contacts — POST a handful of contacts via the API. The list should populate; mocks step out of the way.
  3. Add a note with hashtag — open a contact, type "first sync #strategic #q3". Confirm two tags appear on the contact + chips render in the note inside the unified timeline.
  4. Reminder kanban drag — drag a reminder from "Today" to "Later". Verify backend persistence (refresh page, check column).
  5. Pre-call modal — click an event in the week agenda. Confirm modal shows the AI brief. With the real backend, this should call Claude (currently mock returns a templated brief).
  6. Pipeline drag — drag a deal between stages. Currently in-memory only — confirm it doesn't crash; persistence requires the Deal model + routes.
  7. Sequences expand — click a sequence row. Verify steps render with the right status colors and rationale lines.
  8. Voice simulator — on /dashboard/voice, click any "Try a capture" button. Confirm the 3-step animation (uploading → transcribing → extracting) runs and prepends a new capture to the list.
  9. Inbox reply — open a message, type a reply, click Send. Currently mock — just confirm the UI moves through Sending → Sent.
  10. Network filter — click each sector pill. Confirm the graph reorganizes and the side panel appears with contacts grouped by company.
  11. Settings toggles — click Connect / Disconnect on each integration card. 700ms delay simulates an OAuth flow; counters update.
  12. Sidebar navigation — verify every link works and the active state highlights correctly.
How to know it's production-ready: the test plan above passes with the backend running and an empty NODE_ENV=production build (no mock fallback triggered). All AI buttons return real Claude responses. The Telegram bot creates real notes/reminders when you send it a voice note.
